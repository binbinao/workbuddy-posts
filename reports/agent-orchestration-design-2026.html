🎯01 · 需求背景与设计目标

在复杂的 AI 应用场景中，单一 Agent 难以胜任全流程任务。我们需要一个编排系统来协调 5-15 个混合型 Agent（核心大模型 + 轻量工具型）协同工作，以 分发-聚合（Fan-out/Fan-in） 为核心协作模式。

∞
环境无关 · 可裁剪

核心设计原则

YAGNI + KISS：不过度设计，优先解决 Fan-out/Fan-in 核心场景，架构预留扩展点但不提前实现。保持各模块可独立替换、可渐进式采用。

🏗️02 · 整体架构概览

系统采用 中心化 Orchestrator + Agent Pool + Message Bus 三层架构。Orchestrator 是"大脑"，负责任务拆解、分发和聚合；Agent Pool 是"手脚"，执行具体任务；Message Bus 是"神经系统"，保障通信解耦。

六大核心模块

🧩

Task Decomposer

将复合请求拆解为可并行的原子子任务，生成有向无环图（DAG）描述任务依赖关系

📡

Dispatch Engine

基于 Agent 能力注册表和当前负载，将子任务路由到最合适的 Agent 实例

🗃️

Context Manager

维护共享上下文池，管理 Agent 间信息传递，支持分级存储和快速检索

🔄

Retry & Fallback

故障检测、指数退避重试、备选 Agent 降级、熔断保护

🧲

Result Aggregator

收集并发子任务结果，冲突检测与合并，输出一致性校验

📊

Observability Collector

全链路追踪（Trace）、状态指标（Metrics）、结构化日志（Logs）三位一体

⚙️03 · 核心模块详设

3.1 Task Decomposer — 任务拆解器

核心能力：将用户的高层请求拆解为结构化的子任务 DAG。支持两种拆解模式：

模式适用场景实现方式
静态拆解 任务类型已知、流程固定 预定义的 DAG 模板 + 参数化填充
动态拆解 任务类型灵活、需智能判断 LLM 驱动的任务分析 + 结构化输出 
// 子任务 DAG 数据结构
interface TaskDAG {
  id: string                    // 任务组 ID
  tasks: SubTask[]              // 子任务列表
  dependencies: Map<string, string[]>  // 依赖关系图
  context_requirements: string[]     // 需共享的上下文 key
}

interface SubTask {
  id: string                    // 子任务 ID
  type: "llm" | "tool" | "hybrid"  // Agent 类型要求
  capability: string            // 所需能力标签
  input: ContextRef             // 输入上下文引用
  timeout_ms: number            // 超时阈值
  retry_policy: RetryPolicy     // 重试策略
  priority: number              // 优先级 (0-10)
}

3.2 Dispatch Engine — 分发引擎

基于 能力匹配 + 负载均衡 + 成本感知 的三维调度策略：

  • 能力匹配：子任务的 capability 标签与 Agent 注册的能力标签做集合匹配
  • 负载均衡：优先分发到当前队列深度最浅的 Agent 实例
  • 成本感知：同等条件下优先选择轻量 Agent（Tool/小模型），节省大模型 Token 消耗

💡 调度优化：Affinity 亲和性

当某个 Agent 已经持有相关上下文时，分发引擎倾向将同组的后续任务分发给它，减少上下文传递开销。这在上下文较大（如长文档分析）时尤其有效。

3.3 Result Aggregator — 结果聚合器

Fan-in 阶段的核心。收集各并发 Agent 的输出，执行三步聚合：

  1. 完整性校验：确认所有必需子任务已返回结果（或已超时/失败处理）
  2. 冲突检测：当多个 Agent 产出涉及同一数据域时，检测矛盾并标记
  3. 结构化合并：按预定义的合并策略（拼接 / 投票 / 权重 / LLM 合成）输出最终结果

🤖04 · Agent 注册与生命周期

Agent 能力注册表

每个 Agent 启动时向 Orchestrator 注册，声明自己的身份和能力。这是分发引擎做路由决策的基础。

// Agent 注册信息
interface AgentRegistration {
  agent_id: string               // 全局唯一 ID
  name: string                    // 可读名称
  type: "llm" | "tool" | "hybrid"
  capabilities: string[]         // 能力标签
  model?: string                  // 底层模型 (LLM Agent)
  max_concurrency: number       // 最大并发处理数
  avg_latency_ms: number        // 历史平均延迟
  cost_per_call: number         // 单次调用成本 (归一化)
  health_endpoint: string       // 健康检查地址

}

🛡️05 · 容错与重试机制

这是系统的"免疫系统"。核心原则：快速失败、智能重试、优雅降级。

5.1 三级容错策略

🔁

L1 · 原地重试

同一 Agent 重试，指数退避（1s → 2s → 4s），最多 3 次。适用于临时故障（网络抖动、API 限流）

🔀

L2 · 切换 Agent

切换到同能力的备选 Agent。适用于 Agent 持续不可用。Dispatch Engine 自动选择替代

⬇️

L3 · 降级处理

返回部分结果 + 降级标记。适用于所有同能力 Agent 均不可用，确保系统不完全阻塞

5.2 重试策略配置

interface RetryPolicy {
  max_retries: number            // 最大重试次数 (默认 3)
  backoff: "exponential" | "linear" | "fixed"
  base_delay_ms: number         // 基础延迟 (默认 1000ms)
  max_delay_ms: number          // 最大延迟 (默认 30000ms)
  retryable_errors: string[]   // 可重试的错误类型
  fallback_agent?: string      // L2 备选 Agent ID
  degrade_response?: any       // L3 降级返回值
}

5.3 熔断器（Circuit Breaker）

⚡ 防止雪崩

当某个 Agent 在滑动窗口（60s）内失败率超过 50% 且失败次数 ≥ 5，熔断器从 CLOSED → OPEN，停止向该 Agent 分发新任务。30s 后进入 HALF-OPEN，放行 1 个试探请求。成功则恢复，失败则继续 OPEN。

     ┌─────────┐   失败率 > 50%   ┌─────────┐
     │ CLOSED  │────────────────→│  OPEN   │
     │ (正常)  │                  │ (熔断)  │
     └────┬────┘                  └────┬────┘
          │                            │
     成功率恢复                     30s 冷却
          │                            │
     ┌────┴────┐    试探失败      ┌────┴────┐
     │ CLOSED  │←────────────────│HALF-OPEN│
     └─────────┘    试探成功      └─────────┘

6.2 上下文条目结构

interface ContextEntry {
  key: string              // 如 "user_query", "search_results"
  value: any               // 任意结构化数据
  version: number          // 乐观锁版本号
  producer: string         // 写入方 Agent ID
  consumers: string[]     // 预期消费方 Agent ID 列表
  ttl_ms: number           // 存活时间
  size_bytes: number       // 数据大小 (用于配额管理)
  created_at: timestamp
}

6.3 三大共享策略

策略适用场景实现方式延迟
引用传递 大数据对象（文档、图片） 只传 context_key，Agent 按需拉取 低
值传递 小数据对象（参数、配置） 直接嵌入任务消息体 最低
订阅推送 实时更新的共享状态 Context Pool 发布变更事件 中

💡 上下文摘要压缩

当上下文过大超出 Agent 的上下文窗口时，Context Manager 自动调用一个轻量 LLM Agent 生成摘要版本。原始数据保留在 Warm Storage，摘要缓存在 Hot Cache。Agent 可按需请求原始或摘要版本。

Fan-out/Fan-in 主流程

详细时序

1 Orchestrator → 接收请求，写入原始上下文到 Context Pool
2 Decomposer → 分析请求，生成 TaskDAG（3 个可并行子任务 + 1 个依赖型子任务）
3 Dispatch → 查询 Agent 注册表，按能力+负载匹配，Fan-out 分发 3 个并行任务
4 Agent A/B/C → 并发执行，各自从 Context Pool 读取输入，写回输出
5 Retry Engine → Agent C 超时，触发 L1 重试（指数退避 1s），第二次成功
6 Dispatch → 3 个并行任务完成，释放依赖型子任务 → 分发给 Agent D
7 Aggregator → 收集全部 4 个子任务结果，执行冲突检测和结构化合并
8 Orchestrator → 输出最终结果，同时写入 Trace/Metrics/Logs

📋09 · 接口协议设计

Orchestrator 与 Agent 之间通过统一的消息协议通信，保持松耦合。

9.1 任务消息格式

// Orchestrator → Agent 的任务消息
interface TaskMessage {
  message_id: string           // 消息唯一 ID
  trace_id: string             // 链路追踪 ID
  task: SubTask                 // 子任务定义
  context_refs: string[]      // 引用传递的上下文 key
  inline_context?: Record<string, any>  // 值传递的小上下文
  deadline: timestamp          // 绝对截止时间
  reply_to: string             // 回复队列地址
}

// Agent → Orchestrator 的结果消息
interface ResultMessage {
  message_id: string
  trace_id: string
  task_id: string
  status: "success" | "error" | "partial"
  result?: any                  // 成功时的输出
  error?: ErrorDetail          // 失败时的错误信息
  context_written: string[]  // 本次写入的上下文 key
  metrics: {
    duration_ms: number
    tokens_used?: number
    memory_peak_mb?: number
  }
}

9.2 Agent SDK 核心接口

// Agent 只需实现这一个接口即可接入编排系统
interface AgentHandler {

  // 声明自身能力 (启动时调用)
  register(): AgentRegistration

  // 执行任务 (核心方法)
  execute(task: TaskMessage, ctx: ContextClient): Promise<ResultMessage>

  // 健康检查
  healthCheck(): HealthStatus

  // 优雅关闭
  shutdown(): Promise<void>
}

// 上下文客户端 (SDK 提供，Agent 使用)
interface ContextClient {
  get(key: string): Promise<any>
  set(key: string, value: any, ttl?: number): Promise<void>
  subscribe(key: string, cb: Function): Unsubscribe
}

🎯 极简接入原则

Agent 开发者只需实现 AgentHandler 接口中的 4 个方法即可接入系统。SDK 封装了消息收发、上下文读写、健康上报、指标采集等所有基础设施逻辑。开发者只关注业务逻辑。
